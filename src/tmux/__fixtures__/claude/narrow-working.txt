● How Terminal Multiplexers Work


  A terminal multiplexer such as tmux or GNU screen lets one ter
minal window host many independent shell sessions. Those
  sessions keep running after you close the window, and you can
reattach from another machine later. The mechanism is
  less magical than it looks. It rests on three ideas: pseudo-te
rminals, a terminal emulator that lives inside the
  multiplexer, and a client-server split connected by a Unix soc
ket.

  The Problem Being Solved


  A shell normally expects a terminal, and the terminal is the p
rogram that displays output and sends keystrokes. When
  you close the window, the terminal emulator exits, the kernel
delivers SIGHUP to the session leader, and the shell and
  its jobs die. A multiplexer solves this by taking over the rol
e of the terminal on the shell's behalf, so the shell's
  lifetime is decoupled from any particular window.

  Pseudo-Terminals: The Foundation

  Unix provides pseudo-terminals (PTYs) as pairs of file descrip
tors. The master side is held by a controlling program,
  and the slave side is presented to a process as its terminal d
evice (/dev/pts/N). Bytes written to the master appear
  as input on the slave, and output written by the slave is read
able from the master.

  A multiplexer opens one PTY pair per window (called a "pane" o
r "window" depending on the tool). It forks, makes the
  slave the controlling terminal of a new session with setsid(),
 and execs the user's shell. The shell believes it is
  talking to a real terminal, and the multiplexer holds the mast
er end. Because the server owns the master descriptors,
  the shell's terminal does not disappear when any client discon
nects.

  The Client-Server Split

  Most multiplexers run as two kinds of process:

  - The server is a long-lived daemon. It owns all PTY masters,
all shell processes, and the state of every window and
    pane. It listens on a Unix domain socket, typically under /t
mp/tmux-UID/default for tmux.
  - The client is the program you run in your real terminal. It
connects to the socket, puts your terminal into raw
    mode, forwards keystrokes to the server, and paints whatever
 the server sends back.

  When you run tmux attach, you are starting a client. When you
detach with Ctrl-b d, the client exits and the server
  continues. Because the server owns the processes, closing the
client does not affect them. Starting a new client
  against the same socket gives you the same sessions again. Mul
tiple clients can attach to one session, and tmux
  resizes the view to the smallest attached client by default.

  Parsing Output: The Virtual Terminal

  Shell output is not simply copied to the screen. Programs emit
 escape sequences: cursor movement (ESC [ 10 ; 20 H),
  colors (ESC [ 31 m), clearing lines, scroll regions, alternate
-screen switching for editors like vim, and mouse
  reporting. The multiplexer must understand these, because it h
as to maintain the correct contents of every pane even
  when no client is watching.

  So each pane has a virtual screen: an in-memory grid of cells,
 each holding a character and its attributes, plus a
  cursor position and a scrollback buffer. As bytes arrive from
the PTY master, the server runs them through a
  terminal-emulator state machine (following standards such as t
he DEC VT100 family and xterm). Printable characters are
  written into the grid, and control sequences update the cursor
, attributes, and scroll region. This is why a
  multiplexer can restore a full-screen application exactly when
 you reattach, and why its scrollback and copy mode work
  even though the outer terminal never saw that history.

  Rendering to the Real Terminal


  The server composes all panes in a window into one logical scr
een, adds borders and a status line, and then has to
  emit escape sequences that make your real terminal look the sa
me. It does not redraw everything on each change. It
  keeps a model of what the client terminal last displayed and c
omputes a minimal diff, emitting only the cells that
  changed. This keeps latency low over slow SSH links and avoids
 flicker.

  Input flows the other way. The client forwards raw keystrokes
to the server. The server checks them against its prefix
  key (Ctrl-b by default) and key bindings. Ordinary keys go to
the active pane's PTY master, and prefix commands are
  handled internally. Mouse events and bracketed paste are trans
lated according to the active pane's requested modes.

  Resizing and Signals

  When the terminal window changes size, the client sends the ne
w dimensions to the server. The server resizes each
  affected pane's virtual screen, calls ioctl(TIOCSWINSZ) on the
 PTY master, and the kernel delivers SIGWINCH to the
  foreground process group inside that pane. Programs like vim a
nd less then redraw themselves. Because the server owns
  the resize logic, each pane can have a different size from its
 neighbors.

  Process Management and Cleanup

  Each pane's shell is its own session leader with its own contr
olling PTY, so job control (Ctrl-z, fg) works normally
  inside it. When a shell exits, the server notices the closed P
TY, removes the pane, and rearranges the layout. If the
  last pane in a window closes, the window closes. If the last w
indow in a session closes, the session ends, and when
  the server has no sessions left, it may exit.


  Why the Design Matters

  The architecture trades a small amount of complexity for signi
ficant flexibility. The server holds the authoritative
  state, so clients are disposable. Emulating the terminal insid
e the multiplexer allows features such as scrollback
  search, synchronized panes, and reattachment to full-screen pr
ograms. The main costs are a second layer of
  escape-sequence handling, which occasionally disagrees with th
e outer terminal on newer features, and the need to pass
  through capabilities like true color and clipboard access care
fully. Understanding the server, the PTY pairs, and the
  virtual screen explains nearly every behavior users notice, fr
om why detaching keeps programs running to why a pane's
  colors may look slightly different from the window's.
